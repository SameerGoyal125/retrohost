# Retrohost — Demo Script (~3 minutes)

**Premise:** Retrohost is a paper-reproduction auditor on TrueForge. Give it a
paper's public GitHub repo; it re-runs each figure's analysis in an isolated
sandbox, scores which reproduce, shows the divergent figure's diff, and pauses
for your approval before publishing a public reproduction report.

**Target:** Best Use of TrueForge track (NVIDIA DGX Spark). The demo must show
the harness doing real work — a real tool reached (GitHub MCP), untrusted code
run in the sandbox, a pause before the irreversible public post, work handed to
subagents, and a session that survives a reconnect.

---

## Beat 1 — Ingestion + fan-out (~45s)

**On screen:** TrueForge chat UI. Type:

```
Reproduce the figures in <owner>/divergent-paper
```

**What the viewer sees:** the agent reads the repo via the GitHub MCP connector,
enumerates the figure, and fans out a subagent (visible in the agent-steps panel
as a `thread.created` event).

**Narration:** "Retrohost reads the paper's public repo through the GitHub MCP
connector, finds the analysis script and its claimed result, and hands the
reproduction to a subagent. The paper's code is untrusted — it runs isolated in
the sandbox, where credentials never enter. That's the harness's safety
boundary."

---

## Beat 2 — Scorecard + divergent-figure diff (~45s)

**On screen:** the Generative UI scorecard renders: per-figure status
(REPRODUCED / PARTIAL / FAILED), counts, and — for the divergent figure — the
side-by-side diff of the claimed figure vs the reproduced figure.

**Narration:** "The scorecard shows this figure does not reproduce. Here's the
side-by-side diff — the claimed result on the left, what the code actually
produces on the right. The committed result is stale: it was generated by an
older version of the script. This is the 'aha' moment — the agent computed the
classification in code, not guessed it."

---

## Beat 3 — Clarifying question (~20s)

**On screen:** the agent asks via the clarifying-question card:

> Post the reproduction report as a public GitHub issue on `<owner>/<repo>`?
> - Post as public issue
> - Hold for my review

**Narration:** "Retrohost asks before acting. I'll choose 'Post as public issue'."

Click **Post as public issue**.

---

## Beat 4 — Approval pause (~40s)

**On screen:** the agent calls `create_issue`; the harness PAUSES and shows the
issue title + body with **Allow / Deny** buttons.

**Narration:** "This is the moment that matters. The agent is about to make a
public, attributed claim about a paper's reproducibility. That's a one-way door
for reputation — even if the issue can later be deleted, the attribution
doesn't go away. So the harness stops and asks a person before anything
irreversible happens. I'll click Allow."

**On screen:** click **Allow** → the issue is created on the repo.

---

## Beat 5 — Session persistence (~30s)

**On screen:** refresh the browser tab mid-review (or show SDK resume via
`getTurn` + `subscribeToTurn`).

**Narration:** "The session survives the refresh — the conversation, the
scorecard, and the pending approval are all still there. TrueForge persists the
session, so a long reproduction review can be resumed after a reconnect."

---

## Timing note

If the demo runs long, **cut Beat 5** (session persistence). Beat 4 — the
approval pause — is the control-and-safety criterion and must stay.

## Honest framing

- Do **not** claim the issue is "irreversible because you can't delete it."
  Frame it as "public + attributed + reputationally consequential."
- Post only to a repo where you have `issues:write` (a real small paper's repo
  or a fork you control).
- State the honest scope: Retrohost reproduces **Python-based** paper code;
  R/notebook/shell papers classify FAILED with the reason.
